# TrustVault Threat Model & Security Architecture (THREATS.md)

## 2. Trust Assumptions & Honest Limitations

1. **Database-Resident Hash Chain Trust Assumption**:
   A cryptographic hash chain stored inside PostgreSQL/SQLite guarantees that *unauthorized updates, silent deletions, or sequence disruptions are immediately detected*. However, an attacker who obtains complete superuser access to the database could theoretically rewrite the entire table and recompute all hashes from scratch. To achieve true non-repudiation against superuser compromises, the latest chain head hash should be periodically anchored to an immutable external ledger or write-once-read-many (WORM) storage bucket.
2. **Signed URLs vs. Authenticated Download Proxy**:
   While pre-signed object storage URLs can offload network bandwidth, they introduce a fundamental revocation weakness: an issued pre-signed URL remains valid until its timestamp expires, creating a window where a revoked user can still download content. TrustVault deliberately implements an **authenticated application download proxy**, ensuring immediate, zero-lag revocation on every single byte request.
3. **Antivirus Scanning**:
   TrustVault validates cryptographic file headers (magic bytes), file extensions, and MIME structures. However, heuristic malware/macro scanning (e.g., ClamAV, AWS GuardDuty) requires an external antivirus scanner daemon, which can be connected via the documented integration hook in `lib/validation/upload.ts`.
